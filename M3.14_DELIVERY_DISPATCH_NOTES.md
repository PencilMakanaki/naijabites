# M3.14 — Delivery assignment and customer tracking

## Included
- Restored the rider onboarding dependency missing from the current project archive: customer application, admin approval/rejection/suspension, rider role activation, and rider sign-in route.
- Rider onboarding: `GET /api/v1/riders/mine`, `POST /api/v1/riders/apply`; admin review: `GET /api/v1/admin/riders`, `POST /api/v1/admin/riders/:id/decision`
- Rider application UI: `/rider-portal` and `/rider/apply`; admin verification UI: `/admin/riders`
- Admin dispatch queue: `GET /api/v1/admin/deliveries`
- Assign/reassign before acceptance or pickup: `POST /api/v1/admin/deliveries/:orderId/assign` with `{ riderId }`
- Rider assignments: `GET /api/v1/rider/deliveries`
- Rider actions: `POST /api/v1/rider/deliveries/:id/accept|reject|pickup|transit|complete`
- Customer tracking: `GET /api/v1/me/orders/:id/delivery`
- UI: `/admin/riders`, `/admin/deliveries`, `/rider-portal`, `/rider/deliveries`, `/orders/:id/tracking`

## Workflow rules
- Only paid, active orders can be assigned.
- Only approved rider profiles can be assigned.
- Rider endpoints require a rider-area session and rider role.
- Customers can only retrieve tracking for their own orders.
- A rider can accept or decline an assignment; after acceptance, the rider can confirm pickup, start transit and confirm delivery.
- Delivery completion synchronizes the parent order to `delivered`; pickup synchronizes it to `out_for_delivery`.
- Reassignment is blocked after rider acceptance or pickup.
- Every assignment and rider state transition is stored in `delivery_status_events`.

## Database
- Reuses the V026 `rider_profiles`, `deliveries` and `delivery_status_events` tables.
- V029 extends the delivery status constraint to include `accepted`.
- V030 stores rider review reasons and reviewer metadata.

## Rider onboarding continuity
The clean archive did not include the earlier M3.13 rider onboarding UI/API, so its required application and approval workflow has been restored in this package against the existing V026 `rider_profiles` table. This is a prerequisite for assigning real approved riders. No fake rider accounts are seeded.
